Write structured design briefs that align stakeholders and guide execution. Based on agency-standard brief formats from IDEO, Pentagram, Design Council UK, and AIGA best practices.

## Structure

1. Project overview: what is being designed and why (2-3 sentences)
2. Problem statement: what specific problem this design solves (user perspective)
3. Objectives: measurable outcomes for this project
4. Target audience: who it is for, what they need, what they value
5. Scope: what is included and what is explicitly excluded
6. Deliverables: exactly what will be produced (format, quantity, specs)
7. Timeline: phases, milestones, review points, final delivery
8. Success criteria: how we know it is done well (testable, specific)
9. Constraints: budget, technology, brand, legal, timeline

## Sections Detail

### Project Overview
2-3 sentences. If it takes longer to explain, the project is not defined well enough. State the design challenge, the product/service, and the expected outcome. "Redesign the checkout flow for the mobile web app to reduce cart abandonment below 60%."

### Problem Statement
Must be from the user perspective, not the business perspective. "Users cannot find the checkout after adding items to cart" not "We need to redesign the checkout page." Use the format: "[User] cannot [goal] because [barrier]."

### Objectives
Must be measurable. Use SMART criteria:
- Specific: "Improve task completion rate" not "Improve experience"
- Measurable: "from 45% to 70% within 3 months"
- Achievable: realistic given constraints
- Relevant: tied to business or user need
- Time-bound: "by Q3 2026"

### Target Audience
Include: demographics, behaviors, goals, pain points, current solutions they use, level of expertise, context of use. Avoid vague "everyone" targeting — define the primary user, secondary users, and stakeholders separately. Add an "anti-audience" section: who this design is NOT for.

### Scope
| In scope | Out of scope |
|----------|--------------|
| Mobile web checkout flow | Desktop redesign |
| Payment form with 3 fields | New payment provider integration |
| Error handling and validation | Multi-language support |
| 1 round of usability testing | Ongoing A/B testing program |

### Deliverables
Be specific about exactly what will be produced:
- Design files (Figma, Sketch, Adobe XD)
- Prototype fidelity (low, mid, high)
- Documentation (design system, handoff, spec)
- Assets (icons, illustrations, exports)
- Number of revision rounds included

### Timeline

| Phase | Duration | Activities | Deliverable | Review point |
|-------|----------|------------|-------------|--------------|
| Discovery | Week 1 | Stakeholder interviews, competitive audit, user research | Research report | End of week 1 |
| Design | Weeks 2-3 | Wireframes, visual design, prototyping | High-fidelity mockups | Mid-week 2, end week 3 |
| Testing | Week 4 | Usability testing with 5 users | Test report + iterations | End of week 4 |
| Handoff | Week 5 | Design spec, asset export, developer walkthrough | Handoff package | End of week 5 |

### Success Criteria

| Criteria | Measurement | Target |
|----------|-------------|--------|
| Task completion rate | Usability test | > 80% first attempt |
| Time on task | Analytics | < 90 seconds |
| User satisfaction | SUS score | > 75 |
| Developer handoff | Questions post-handoff | < 5 clarifications |
| Accessibility | WCAG audit | WCAG 2.1 AA |

### Constraints
- Budget: hard and soft limits
- Technology: platform, framework, CMS limitations
- Brand: colors, fonts, voice restrictions
- Legal: compliance (GDPR, WCAG, HIPAA), trademark
- Timeline: hard deadlines, drop-dead dates
- Technical: load time, bundle size, SEO requirements

## Stakeholder Alignment Questions

Before finalizing the brief, ensure these questions have answers:
1. Who has final approval on the design?
2. What happens if we don't meet a deadline?
3. What is the single most important metric for success?
4. What can we deprioritize if scope needs to shrink?
5. Who are we explicitly NOT designing for?
6. What precedent or existing design should we reference?
7. What are the non-negotiables (legal, brand, technical)?

## Anti-Patterns

| Mistake | Consequence | Fix |
|---------|-------------|-----|
| Problem stated as solution | Team builds the wrong thing | Describe the problem, not the fix |
| No constraints given | Design that cannot be built | List technology, budget, timeline limits |
| Vague success criteria | No way to know when it is done | Define specific, testable criteria |
| Scope creep hidden in "also" | Timeline and budget blown | List exclusions explicitly |
| No stakeholder sign-off | Designs rejected late in process | Get written approval on the brief |
| Audience too broad | Design serves no one well | Define primary + secondary + anti-audience |
| Timeline without buffer | Missed deadlines, rushed quality | Add 20% buffer for unknowns |
| Missing "why" | Team makes wrong trade-offs | Include the business and user rationale |
